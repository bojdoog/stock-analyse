**Assistant**

找到了。原因是 **CSV 中缺失的 `net_inflow` 字段被 `parseFloat(...) || 0` 默认设为了 `0`**。

比如某个板块在某天数据缺失（空字符串），`parseFloat('')` 返回 `NaN`，然后 `|| 0` 把它变成了 `0`。这个 0 不是真实数据，只是占位符。

在排名时，真实的净流入可能是负数（比如 -10 亿），而缺失数据被当作 0，这个伪造的 0 会排在 -10 亿前面，导致：
1. 一个实际上没有资金流入数据的板块（显示为 0 亿）被错误地排在前列
2. 真正有数据但净流入为负的板块被挤掉
3. 最终持仓数少于 5 个，因为有多个"假 0"占据了名额，而真实数据里只有 4 个有效条目

修复内容：
1. **index.tsx** — `net_inflow` 解析改为 `isNaN(v) ? NaN : v`，保留 NaN 作为缺失标记
2. **backtest.ts** — `getMoneyflowInflow` 和 `getConceptInflow` 增加 `!isNaN(item.net_inflow)` 校验，跳过缺失数据
3. 排名逻辑中已有的 `!isNaN(g.inflow)` 过滤器会自动过滤掉无效条目

现在没有数据的板块会被正确跳过，只有真实的资金流向数据参与排名。

## 优化方案

### 方案 1：前端文件合并（零架构改动）

**思路**：将零散的 CSV 文件合并成少量大文件

**做法**：
- 写预处理脚本，将每个资金流向目录的所有 CSV 合并成 `{name}_all.json`
- 按年份合并为 `moneyflow_2023.json`、`moneyflow_2024.json`...
- 前端只按需加载选中年份的文件

**请求数变化**：1615 → 3~5 个
**优点**：不改架构，纯前端
**缺点**：合并后文件可能很大（~3MB/年），首次加载仍慢；每年需要手动合并

---

### 方案 2：前端按需加载 + 索引（零架构改动）

**思路**：保留 CSV 文件，但前端只加载需要的

**做法**：
- 保留 `index.json` 记录文件列表
- 前端根据回测年份范围，只加载涉及的日期文件
- 加 localStorage 缓存，已加载的不重复请求

**请求数变化**：最多 1615 → 按需（如查 2024 年只加载 240 个）
**优点**：改动小，灵活
**缺点**：仍需多次请求，缓存首次命中前仍慢

---

### 方案 3：轻量 Node.js/Python 后端（推荐）

**思路**：加一层薄后端处理资金流向

**做法**：
- 用 Express/Python Flask 写简单 API
- 接口示例：`GET /api/moneyflow?start=20240101&end=20241231&type=dc`
- 后端读取 CSV 聚合后返回 JSON
- ETF/Index 数据仍前端加载（3MB 不大）

**架构**：
```
前端 → /api/moneyflow → 后端读取CSV → 返回聚合数据
      → /data/etf/*.csv    → 直接加载（27个文件）
      → /data/index/*.csv  → 直接加载（2个文件）
```

**优点**：
- 前端只 29 个请求（ETF+Index）
- 资金流向 1 次请求搞定
- 后端可以做缓存、压缩
- 可以扩展更多功能

**缺点**：需要部署后端服务

---

### 方案 4：Serverless 函数（Vercel/阿里云函数计算）

**思路**：无服务器后端

**做法**：
- 把 CSV 数据放 Serverless 可访问的存储
- 写一个 Serverless Function 处理查询
- 前端调用 API

**优点**：不用维护服务器，按量付费
**缺点**：冷启动延迟，数据量大时函数超时

---

### 方案 5：SQLite + 后端（长期方案）

**思路**：用数据库替代文件

**做法**：
- 把所有 CSV 导入 SQLite
- 后端用 SQL 查询
- 可以做复杂分析

**优点**：查询灵活，支持聚合/排序
**缺点**：需要建表、导入、维护

---

### 方案 6：预计算 JSON（折中方案）

**思路**：构建时预计算好常用数据

**做法**：
- 构建时脚本计算好每个 ETF 的年度排名结果
- 生成 `precomputed/2024_etf_rankings.json`
- 前端只加载预计算结果

**优点**：前端零计算，加载极快
**缺点**：需要定期重新预计算

这种情况确实可以想办法过滤，但每种过滤方式都有代价：**少亏假突破的同时，也可能错过真启动**。

从你截图看，2024 年那几个失效的多头区间有几个共同特征：

- 持续时间短（几天到一两周）
- 涨幅很小，甚至微亏
- 往往是反弹一日游/两日游，不是趋势性上涨

下面几种思路可以规避一部分：

## 1. 增加「确认日」延迟

不选在启动日当天买入，而是等启动后第 2 天或第 3 天仍满足某种条件再买入。比如：
- 启动后次日收盘仍高于启动日收盘价
- 启动后连续 2 日不跌破 MA10

这样能过滤掉很多一日游脉冲。

## 2. 设置最小持续时间门槛

多头区间结束后，只有**持续天数 ≥ N 天**的才纳入交易，短的直接忽略。比如：
- 持续 < 5 天的波段不交易
- 但这样可能把「短暂但暴利」的波段也过滤掉

## 3. 设置最小涨幅/振幅门槛

启动日之后的几天内，区间累计涨幅要达到一定水平才确认是有效波段。比如启动后 3 个交易日内累计涨幅 ≥ 3%，否则视为假信号。

## 4. 结合成交量或市场整体广度

单独看活跃市值可能被骗线，可以叠加：
- 启动日成交量明显放大
- 多个板块 ETF 同时出现动量，不是单一板块脉冲
- 上证指数/沪深 300 同步上涨，避免个股行情

## 5. 提高启动阈值

当前是单日 > 4% 或两日累计 > 4%。可以提高到 5% 或 6%，减少毛刺信号。但会错过一些温和启动。

## 6. 引入「趋势背景」过滤

只在活跃市值处于某种中长期趋势向上时才参与多头。比如：
- 活跃市值收盘价在 MA20 上方
- 或者 MA10 本身正在走平/向上

这样就不会在一路下跌中反复抄底。

这个结果是**数学上优化出来的，但现实意义不强**，本质上是过拟合了。

## 为什么增长最优会给出这种奇怪比例？

增长最优的算法是：穷举所有权重组合，找出让历史各多头区间 **(1 + 区间收益)** 乘积最大的那一组。

也就是说，它只关心一件事：**历史上哪个名次的 ETF 曾经创造过巨大的区间收益**，就往哪个名次猛配仓位。

如果算出来是：

```
第3名 70%   第5名 30%   其他 0%
```

说明在 2019~2026 年的历史多头区间里：
- 第 3 名的 ETF 曾经在某几个区间涨幅特别夸张
- 第 5 名也在某些区间表现突出
- 而第 1、2、4 名的历史区间收益相对平庸

所以优化器为了「总净值最大」，就把所有筹码压到了历史表现最好的两个名次上。

## 这有什么问题？

1. **过拟合**：它只是对历史数据做拟合，未来的名次收益分布未必和过去一样。
2. **名次不是独立变量**：第 1 名是启动日涨幅最大的 ETF，理论上应该最强。但历史上可能碰巧某几次第 3、第 5 名后来涨得更多。
3. **结果不稳定**：换一个时间段（比如 2021~2024），最优比例可能完全不同。
4. **缺乏分散**：70%/30%/0/0/0 这种集中度风险很高，一旦这两个名次未来表现不好，回撤会很大。

## 建议

可以，ECharts 完全支持这种自定义需求。通过 `itemStyle.color` 回调函数，你可以根据数据条件动态设置 K 线颜色。

```javascript
// 示例：涨幅 > 4% 的 K 线显示为黄色
series: [{
  type: 'candlestick',
  data: data,
  itemStyle: {
    color: (params) => {
      const [open, close, low, high] = params.value;
      const change = (close - open) / open * 100;
      // 涨幅超过 4% 显示黄色
      if (change > 4) return '#FFD700';
      // 默认红涨绿跌
      return close > open ? '#ef5350' : '#26a69a';
    }
  }
}]
```

更复杂的条件（比如结合你的"活跃市值"字段）也可以通过 `data` 数组传递额外信息，在回调里判断。
